## 1. Executive Summary

Artix is a React 18 + TypeScript single-page application built with Vite. It combines a developer workspace (projects, documents/editor, folders, system-design canvas), client-side AI-provider integrations, subscription billing, and a local-first collaboration/synchronization subsystem. The frontend uses Supabase for authentication, server persistence, realtime signals, and Edge Functions; Dexie/IndexedDB stores account-scoped documents, system designs, folders, sync metadata, conflicts, and an outbox. The repository also includes PostgreSQL migrations, billing Edge Functions, PWA/service-worker configuration, Vitest unit tests, Playwright E2E specifications, and CI workflows.

The most consequential issue found in this pass is a **high-confidence synchronization correctness defect**: the client advances a durable pull cursor to the maximum visible `sync_changes.sequence`, but the sequence is generated by PostgreSQL identity allocation, not transaction commit order. A transaction that receives a lower sequence can commit after a transaction with a higher sequence. If the client advances past the higher sequence before the first transaction commits, subsequent `sequence > cursor` queries will skip the late-committing lower-sequence change. This can leave another client permanently missing a remote mutation under ordinary incremental pulls. The existing tests model already-visible ascending sequence rows but do not exercise this commit-order race.

Other findings from the reviewed code are: (1) the checkout Edge Function accepts a caller-supplied Stripe `priceId` without a server-side allowlist, while the webhook grants Pro based on subscription metadata/status rather than verifying the purchased price; (2) the mutation idempotency ledger is written in a separate request after the business mutation, so an acknowledgement lost after server commit can cause a retry to execute the mutation again; (3) free-tier quotas use an unlocked count-then-insert trigger and are raceable under concurrent inserts; (4) the PWA broadly caches Supabase API responses, a credible private-data cache-isolation risk that needs a browser/header-level reproduction; and (5) the documented E2E command references Playwright, but its package is absent from the reviewed package manifest/lockfile and it is not run by CI.

The architecture shows deliberate effort around local-first writes, scoped IndexedDB, an outbox, revision tracking, compare-and-swap updates, RLS, stale-lease recovery, and fault-oriented tests. Those mechanisms are meaningful, but the code review found gaps at the boundaries where correctness depends on database transaction ordering and atomicity across remote requests. No claim is made here that the app is broadly insecure or that every subsystem has been fully audited.

### 3.4 Critical flows traced

**Local workspace write → cloud push**

1. UI hook obtains a user-scoped repository/runtime.
2. Repository persists the entity update, outbox operation, and sync metadata in a Dexie transaction.
3. The leader sync runtime drains ready pending outbox entries.
4. The engine marks an entry in flight with a lease and dispatches an entity-specific push adapter.
5. Adapter requests the target table with a version predicate when a usable base server version is present.
6. After a successful response, the engine marks the entry complete and acknowledges the local revision in sync metadata.

Relevant implementation: [`src/lib/sync/syncEngine.ts#L244-L333`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/syncEngine.ts#L244-L333) and [`src/lib/sync/adapters/documentPushAdapter.ts#L14-L87`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/adapters/documentPushAdapter.ts#L14-L87).

**Cloud change → local replica**

1. PostgreSQL triggers write row changes to `public.sync_changes`.
2. `PullEngine` queries records with `sequence > server_cursor`, ordered ascending.
3. Pull applies a batch in a Dexie transaction; if local outbox intent conflicts with a remote update, it records conflict metadata and preserves local pending intent.
4. The maximum applied sequence is written to `database_meta` as the next cursor.

Relevant implementation: [`supabase/migrations/20260928130000_durable_sync_changes.sql#L6-L20`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/migrations/20260928130000_durable_sync_changes.sql#L6-L20), [`supabase/migrations/20260928130000_durable_sync_changes.sql#L44-L125`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/migrations/20260928130000_durable_sync_changes.sql#L44-L125), and [`src/lib/sync/pullEngine.ts#L77-L123`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/pullEngine.ts#L77-L123).

**Subscription checkout → entitlement**

1. Pricing UI supplies the price ID and origin to `create-checkout-session`.
2. Edge Function authenticates the user, checks origin allowlisting, and asks Stripe to create a subscription checkout session using that supplied price ID.
3. Stripe webhook verifies the Stripe signature, reads `supabase_user_id` from subscription metadata, and writes `plan_tier: 'pro'` and `status: 'active'` on completed checkout.

Relevant implementation: [`src/pages/Pricing.tsx#L18-L44`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/pages/Pricing.tsx#L18-L44), [`supabase/functions/create-checkout-session/index.ts#L18-L42`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/functions/create-checkout-session/index.ts#L18-L42), [`supabase/functions/create-checkout-session/index.ts#L74-L97`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/functions/create-checkout-session/index.ts#L74-L97), and [`supabase/functions/stripe-webhook/index.ts#L42-L64`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/functions/stripe-webhook/index.ts#L42-L64).

## 5. Detailed Subsystem Reviews

### SS-01 — App shell and authentication/session

The application bootstraps all major providers under `React.StrictMode`, including `AuthProvider` and `UserSyncRuntimeProvider`. The Supabase browser client persists the session via localStorage and uses PKCE. `useAuth` listens to `onAuthStateChange` and also calls `getSession()` during initial mount.

The critical coupling is that account changes cause the runtime provider to open/close user-scoped persistence and sync infrastructure. The intended separation is sensible, but this audit did not exercise sign-in/sign-out during initialization, rapid account switching, browser reloads with a pending sync, or session-expiration behavior. `UserSyncRuntimeProvider` marks itself ready after runtime-open failure while logging the error; downstream UX/error propagation deserves targeted review so a failed local DB open is not mistaken for a usable workspace runtime.

**Disposition:** Partially reviewed. No authentication bypass is established by this pass. Follow-up: add tests for initial `getSession()` racing with auth-state events, user-switch cleanup, and fatal IndexedDB-open failure rendering.

### SS-02 — Project metadata and cloud-only operations

`useProjects` fetches projects from Supabase and computes per-project document/design counts by retrieving their project IDs and aggregating in the browser. That means counts require downloading all matching rows rather than server-side grouped counts; this may scale poorly for high record counts, but no performance measurement is available. Project CRUD is direct to Supabase, unlike document/folder/design mutations that go through local repositories.

Client-side duplicate project-name checks compare the locally loaded project list. They can improve UX but do not guarantee uniqueness across concurrent requests or independent clients unless a database constraint enforces the same invariant. No full project schema/constraint audit was completed here.

**Disposition:** Partially reviewed. Follow-up: inspect project schema/constraints, pagination/data volume, uniqueness behavior, and concurrent duplicate creation; decide whether aggregate counts should be SQL/RPC-backed.

### SS-03 / SS-04 — Local persistence and outbox

`ArtixDB` declares local entity tables plus `outbox`, `sync_metadata`, `conflicts`, and `database_meta`. User-scoped DB names isolate most browser-local state by account. Repository writes are intended to combine entity updates with outbox and sync metadata in one IndexedDB transaction. The outbox compacting rules reduce redundant work: pending create+update merges into create; create+delete cancels; update+update merges payloads; update+delete converts to delete.

These are valuable invariants, but the DB schema shown in `src/lib/local/db.ts` currently declares schema version 1 and the repository includes legacy migration helpers. This audit sampled those paths without testing upgrade/migration interrupted-state recovery or a real browser storage quota failure. The client’s 32-bit user hash is not a cryptographic identity; while collision probability is low for typical account counts, account-scoping correctness should not rely solely on the hash being collision-free. The runtime also passes the actual `userId` in entity rows and outbox queries, which provides a second logical scoping layer.

**Disposition:** Partially reviewed. No specific corruption defect confirmed in sampled repository methods. Follow-up: migration/restart tests, storage quota and blocked-upgrade tests, and property-style tests for all compaction transitions under concurrent edits.

### SS-05 / SS-06 — Push, pull, versioning and conflicts

The push engine serially drains pending entries, uses leases, performs an inbound pull before pushing local mutations, routes entities through push adapters, and updates sync metadata when acknowledging a particular local revision. The adapters use server `version` predicates for update/delete when `baseServerVersion` is present and valid. Conflicting updates can be represented in the local `conflicts` store; the pull path attempts to preserve local outbox intent rather than blindly overwriting it.

The primary concern is the change-feed cursor (F-001). The code assumes that an identity-based sequence is a safe committed high-water mark. It is not: identity allocation precedes commit, and transactions can finish in a different order from allocation. An unseen lower sequence can therefore fall behind the committed cursor and be filtered out forever. This is a data-integrity issue because the pull code has no separate mechanism in the inspected path that repairs an omitted feed row by scanning authoritative table snapshots.

A second correctness gap is that the remote mutation and the processed-mutation ledger are separate requests (F-003). The code also ignores Supabase’s returned `{ error }` value from the ledger upsert unless the client happens to throw, because `recordIdempotency` does not inspect the returned result.

Two paths in `pullBatch` use `continue` before the common `maxAppliedSequence` update. The remote-delete convergence path can therefore revisit its event on the next pull; a stale update against a retained tombstone can repeatedly hold the cursor behind that row until a later visible sequence moves it forward (F-007). This does not by itself establish data loss, but it can produce repeated pulls and, in the convergence case, re-apply the same remote delete before the cursor advances.

**Disposition:** Reviewed with findings. Highest-value work is fixing the feed cursor model and making idempotency atomic at the server boundary. No live PostgreSQL test or fault-injection experiment was run.

### SS-07 — Multi-tab coordination and realtime

`TabCoordinator` uses the Web Locks API where available and `BroadcastChannel` for cross-tab events and sync requests. It defaults to leader status where Web Locks are unavailable (for example, a test environment). `RealtimeSyncManager` listens for relevant table changes and treats realtime as a trigger to sync; the durable feed is still the intended source for catching up after disconnections.

The code has explicit listener cleanup, a debounced realtime trigger, and stale in-flight lease recovery. No reproduced race is asserted here. Risks that still need browser-level evidence include behavior when Web Locks are missing or rejected in a real supported browser, multiple tabs opening different accounts, a stale leader resuming after a lock handoff, and user logout while an in-flight request is pending.

**Disposition:** Partially reviewed. Test real tabs/browser behavior, not only mocked leadership transitions, including account switching with a pending outbox and service-worker lifecycle.

### SS-08 — Authentication, RLS and security model

The application uses a public/publishable Supabase key in the browser and the Supabase session, while Edge Functions use server-side service-role credentials for privileged operations. The reviewed migration adds user-specific RLS policies to the change feed and mutation ledger; the UI client uses an authenticated user ID in query filters, while row security should remain the real boundary. The Stripe webhook verifies the Stripe signature before mutating subscription state.

This pass did not enumerate every table/policy/grant combination or inspect deployed RLS state. Documentation contains stronger claims than can be established from source alone, so the audit does not certify tenant isolation comprehensively. `SECURITY.md` documents optional client-side AES-GCM encryption for AI API credentials, but default storage obfuscation is reversible and should not be represented as encryption. The source implementation of `MarkdownPreview.tsx` uses `react-markdown` and `remark-gfm`; the reviewed file does not itself import DOMPurify, notwithstanding a repository security guide that describes DOMPurify sanitization. `react-markdown` defaults do not render arbitrary raw HTML unless configured to do so, so this is a documentation/implementation discrepancy, not evidence of an XSS vulnerability by itself.

**Disposition:** Partially reviewed. Follow-up: review RLS on every relevant table and operation, grants and security-definer functions; verify runtime CSP headers; and reconcile security documents with actual code paths.

### SS-09 — AI providers and local key storage

AI providers are invoked directly by client-side `fetch` calls with a user-provided API key in the `Authorization` header (OpenAI path inspected). This keeps Artix from proxying the request but means prompts/document contents are sent to the selected provider. The key helper `src/lib/ai/crypto.ts` uses AES-GCM-256 with PBKDF2/SHA-256, random salt and IV, and 250,000 iterations. `src/lib/ai/storage.ts` also implements a default reversible obfuscation path for keys not protected by the passphrase vault.

No key-exfiltration issue was established in the sampled code. Provider request cancellation/timeouts and maximum response/prompt bounds were not exhaustively checked across all providers; only a representative OpenAI implementation was inspected. The security posture depends heavily on CSP, Markdown/HTML handling, browser extensions and third-party provider policies.

**Disposition:** Partially reviewed. Follow-up: audit timeouts/cancellation and response-size behavior across all providers, test vault locking during in-flight saves/generation, and verify CSP allowances against actual build/runtime needs.

### SS-10 — Stripe checkout and entitlement

The checkout function authenticates the caller and validates the `origin` against a whitelist. It then takes `priceId` directly from JSON, creates a checkout session for that value, and puts the authenticated user ID in subscription metadata. The webhook promotes the user to Pro on a completed subscription checkout if metadata contains `supabase_user_id`. The repository price IDs are configured in `src/lib/plans.ts`, but the Edge Function does not enforce those IDs or a server-side mapping of product, amount, recurring interval and plan tier.

That split makes a trust-boundary mistake: a browser-controlled parameter influences what subscription gets purchased, and the webhook later grants a fixed entitlement without validating which price was purchased. The actual financial consequence depends on Stripe’s live catalog, which was not inspected. The webhook also checks for a prior event and records the event after processing; these are separate operations, so duplicate delivery races should be exercised even though the primary entitlement write is an upsert.

**Disposition:** Reviewed with findings. Enforce price/plan mapping server-side and validate the resulting subscription line items in the webhook before setting entitlement. Test both tampered `priceId` and duplicate/concurrent webhook delivery.

### SS-11 — Workspace UI/editor/system architect

## 7. Synchronization and Consistency Review

### 7.1 Actual model observed

The workspace entities are edited locally first, stored in an account-scoped IndexedDB database, and represented as pending outbox entries until cloud push succeeds. The server also records changes to documents, system designs and workspace folders in an append-only `sync_changes` table through PostgreSQL triggers. The browser reads the change feed by a durable numeric cursor, applies batches transactionally to local IndexedDB, and tracks server versions/local revisions in sync metadata. Update/delete adapters apply conditional version predicates when a valid base version is present. Cross-tab coordination uses Web Locks where supported and BroadcastChannel notifications; Realtime is a wake-up mechanism for sync rather than the sole source of missed changes.

### 7.2 Expected core invariants

1. A successfully persisted local edit retains either a pending outbox entry or a completed server acknowledgement.
2. A remote update must not silently overwrite a newer pending local edit.
3. Acknowledging revision N must not mark later local revision N+1 as fully synced.
4. Repeating an operation after an ambiguous network result must not replay the business effect or overwrite a later remote value.
5. The pull cursor must never move beyond any server change that remains unseen and will never be returned by later incremental queries.
6. Changes from one user must not be applied to another user’s local data.
7. Delete/update races must converge according to explicit conflict/tombstone semantics.

The code contains mechanisms intended to protect invariants 1–4 and 6–7. Invariant 5 is violated by the current identity-sequence high-water-mark design (F-001). Invariant 4 is not guaranteed because of the non-atomic idempotency ledger (F-003).

### 7.3 Pull-cursor failure timeline

1. Database transaction A updates a document, executes the change-feed trigger, and receives identity sequence `N`. Transaction A remains uncommitted.
2. Transaction B updates a different row for the same user, receives `N+1`, then commits.
3. A client pull query runs while B is committed but A is still uncommitted. It can see `N+1` but cannot see `N`.
4. `pullBatch` applies the visible rows and writes the maximum observed sequence (`N+1`) to local `database_meta`.
5. Transaction A commits later; the `N` row is now visible.
6. Subsequent pulls use `.gt('sequence', N+1)`, excluding A’s row forever unless a separate full reconciliation mechanism happens to repair the omission.

This follows from PostgreSQL identity allocation/transaction visibility and the implementation’s cursor query/update logic. It has not been reproduced against a live database in this audit.

### 7.4 Retry/idempotency failure window

1. A push adapter queries `processed_mutations` and does not find the mutation ID.
2. It performs the business mutation in a separate PostgREST request.
3. The database mutation commits, but the client times out or loses the response.
4. Because the await rejects, client code never reaches `recordIdempotency`.
5. The outbox is retried. A fresh ledger lookup still returns no record, so the adapter re-executes the mutation.

For a create implemented as an `upsert` with a reused entity ID, a replay can update the existing row using the old create payload; it may overwrite data modified after the first commit and increment server version/change-feed state again. The exact resulting harm depends on interleaving, but the claimed safe-retry property is not established by the implementation.

### 7.5 Fault-injection tests required

- Two real PostgreSQL transactions for one user: allocate change-feed sequences in order A then B, commit B then A, and demonstrate that a client cursor at B skips A.
- Commit a remote mutation, intentionally drop the response before client acknowledgement, then retry the same operation; assert one business effect and a stable acknowledgement.
- Two concurrent tabs editing one entity, including edit while the prior revision is uploading and a delayed earlier response.
- Delete-versus-update, tombstone-vs-stale-update, server rejection and cursor progress.
- Kill/reload the tab after local persistence, after `markInFlight`, after remote commit, and before local acknowledgement.
- Logout/account switch while an outbox mutation is pending; verify no write is sent under a different account context.
- Same-user concurrent creates at a usage limit; verify the database never commits over quota.

## 10. Detailed Finding Records

### F-001 — Change-feed cursor can skip late-committing lower sequence values

- **Category:** `SYNCHRONIZATION`, `DATA_INTEGRITY`
- **Severity:** High
- **Confidence:** High
- **Affected components:** `SS-06`, `SS-05`; `supabase/migrations/20260928130000_durable_sync_changes.sql`; `src/lib/sync/pullEngine.ts`
- **Evidence:** The migration declares `sequence BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` and indexes `(user_id, sequence)` ([migration lines 6–20](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/migrations/20260928130000_durable_sync_changes.sql#L6-L20)). Triggered changes are inserted during entity write transactions ([migration lines 44–125](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/migrations/20260928130000_durable_sync_changes.sql#L44-L125)). The client filters `sequence > currentCursor`, orders ascending, and limits the batch ([pull engine lines 77–123](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/pullEngine.ts#L77-L123)); then persists `maxAppliedSequence` as the cursor ([pull engine lines 311–329](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/pullEngine.ts#L311-L329)).
- **Observed behavior:** The cursor represents the largest *currently visible identity value*, not a guarantee that every smaller sequence has committed and become visible.
- **Expected invariant:** Advancing the cursor must imply that every relevant preceding committed change has been observed or will still be returned by a future query.
- **Execution trace:** Transaction A obtains sequence N and remains open; transaction B obtains N+1 and commits; the client sees N+1 but cannot see A’s uncommitted row, advances to N+1, and thereafter asks only for rows greater than N+1; A later commits N, which is now below the cursor.
- **Impact:** A client may never receive a committed remote mutation via the incremental feed. This can cause documents, folders or system designs to remain stale across devices until another independent mechanism repairs them.
- **Prerequisites:** Overlapping database transactions whose trigger insert sequence allocation order differs from commit order, plus a pull occurring after the higher sequence commits and before the lower one commits.
- **Verification:** High confidence from the implementation and database semantics; live two-transaction reproduction not run. Current pull tests use already-visible ordered mocks and do not model late commit order ([`pullEngine.test.ts#L78-L170`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/test/sync/pullEngine.test.ts#L78-L170)).
- **Recommended remediation:** Replace the identity high-water mark with a commit-safe feed cursor contract. Options include per-user serialized sequence assignment using an appropriately locked cursor row that is held until transaction commit, or a server-generated commit-ordered change position. A robust alternative is an overlapping/reconciliation protocol that can recover unseen lower-sequence rows; simply polling the same `sequence > cursor` query cannot repair this gap.
- **Regression protection:** Integration-test concurrent transactions with reversed commit order and prove that every committed entity change eventually reaches the replica, even when a higher allocated sequence commits first.
- **Related findings:** F-007 (cursor progress edge cases).

### F-002 — Checkout price is caller-controlled; webhook does not validate purchased price

- **Category:** `SECURITY`, `CONFIGURATION` (billing authorization)
- **Severity:** Medium (raise if a mispriced/unentitled recurring Price exists)
- **Confidence:** High that server validation is absent; actual financial exposure depends on external Stripe configuration
- **Affected components:** `SS-10`; `src/pages/Pricing.tsx`; `supabase/functions/create-checkout-session/index.ts`; `supabase/functions/stripe-webhook/index.ts`
- **Evidence:** UI submits `priceId` from the browser ([Pricing lines 18–27](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/pages/Pricing.tsx#L18-L27)). The Edge Function reads caller-provided `priceId` and only checks that it and `origin` are present ([checkout lines 34–42](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/functions/create-checkout-session/index.ts#L34-L42)), then passes the same ID to Stripe ([checkout lines 74–86](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/functions/create-checkout-session/index.ts#L74-L86)). On checkout completion the webhook grants Pro based on subscription metadata and the fact that it is a subscription, without checking purchased price ID, amount, product or recurring interval ([webhook lines 44–64](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/functions/stripe-webhook/index.ts#L44-L64)). Known UI price IDs are only in client-side config ([plans lines 36–48](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/plans.ts#L36-L48)).
- **Observed behavior:** The server does not restrict checkout to the intended monthly/annual IDs and the webhook does not verify that a completed subscription purchased a plan entitled to Pro.
- **Expected invariant:** Only an explicitly authorized, correctly priced Artix subscription may produce a Pro entitlement.
- **Execution trace:** An authenticated caller changes the JSON `priceId`; checkout attempts to sell that Stripe Price; if it is a valid recurring price and its subscription metadata links to the caller, the completion webhook marks that user Pro without validating the product/price.
- **Impact:** If the Stripe account has other lower-cost, free/trial, or non-Artix recurring Prices available to this endpoint, a caller could potentially obtain the entitlement under unintended commercial terms. A price that does not exist would simply fail at Stripe, and the existence of a vulnerable alternate live price was not established here.
- **Prerequisites:** The connected Stripe account must contain a usable alternative Price with unintended entitlement economics; the endpoint must be deployed as reviewed.
- **Verification:** Source-level validation gap is confirmed. Live catalog and deployed function configuration not available.
- **Recommended remediation:** Define an explicit server-side map from accepted plan enum to permitted Stripe Price IDs. Do not trust client price IDs. In the webhook, retrieve/inspect the subscription items and validate the Price/Product, amount/currency, interval and status against that map before changing the entitlement row. Reject or quarantine unexpected subscriptions and alert operators.
- **Regression protection:** Edge Function tests tamper with `priceId`; webhook tests show that unknown/unapproved Price IDs never grant Pro, even with a valid signature and correct user metadata.
- **Related findings:** None directly; webhook event de-duplication and transactionality should also be tested.

### F-003 — Remote mutation and idempotency ledger are not atomic

- **Category:** `SYNCHRONIZATION`, `DATA_INTEGRITY`, `RELIABILITY`
- **Severity:** Medium
- **Confidence:** High
- **Affected components:** `SS-05`, `SS-06`; `src/lib/sync/adapters/idempotency.ts`; all entity push adapters
- **Evidence:** The adapter checks the ledger before mutation ([idempotency lines 8–38](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/adapters/idempotency.ts#L8-L38)) but records it in a later independent upsert ([idempotency lines 43–61](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/adapters/idempotency.ts#L43-L61)). A document create first performs an upsert and only then calls `recordIdempotency` ([adapter lines 14–38](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/adapters/documentPushAdapter.ts#L14-L38)). The ledger helper also does not inspect the returned Supabase `{ error }` result. The migration defines the ledger as its own table rather than a mutation RPC ([migration lines 52–72](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/supabase/migrations/20260928120000_server_concurrency_protocol.sql#L52-L72)).
- **Observed behavior:** The entity mutation and idempotency record have separate request/transaction boundaries. A server commit followed by response loss bypasses the client’s ledger-recording call.
- **Expected invariant:** Retrying a mutation after an ambiguous result must return the original acknowledgement without reapplying the mutation or reverting subsequent remote state.
- **Execution trace:** Ledger miss → remote upsert/update/delete commits → response times out before client receives success → client never records mutation ID → retry sees another ledger miss and executes mutation again. For create, replaying the same upsert payload can overwrite values written after the first successful create.
- **Impact:** Duplicate version/change-feed activity is possible; more importantly, an old create payload can replace newer entity content after an ambiguous retry.
- **Prerequisites:** Remote operation commits but response is not successfully received; the ledger write is skipped or fails.
- **Verification:** Directly supported by call ordering; the lost-response mock test does not emulate the actual gap. It pre-populates the mocked ledger as already processed before retry ([`idempotentMutation.test.ts#L125-L144`](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/test/sync/idempotentMutation.test.ts#L125-L144)).
- **Recommended remediation:** Move mutation-ID checking, the entity mutation, durable ledger write and acknowledgement result into a server-side database transaction/RPC so they commit atomically. Use the mutation UUID as the transaction’s idempotency key; subsequent retries should return the stored original result. Avoid create-upsert semantics that overwrite an existing entity with the original create payload unless that behavior is explicitly required and version-guarded.
- **Regression protection:** Fault-inject loss of the response after server commit but before the client receives it; retry with the same mutation ID and assert one applied mutation, unchanged later remote edits and the same acknowledgement version.
- **Related findings:** F-001 can independently leave replicas stale; both issues affect eventual consistency.

- **Prerequisites:** Running `npm run test:e2e` in a clean checkout without an out-of-band Playwright install.
- **Verification:** Manifest/lockfile inspection; command not executed.
- **Recommended remediation:** Add a pinned compatible Playwright test dependency, commit the updated lockfile, install browsers in a CI E2E job, and define whether the browser matrix is required or scheduled. If E2E is intentionally external, document the setup and ownership.
- **Regression protection:** Clean CI install followed by `npm run test:e2e -- --list` and at least one deterministic browser smoke test.

### F-007 — Some pull `continue` branches bypass common cursor advancement

- **Category:** `RELIABILITY`, `PERFORMANCE`
- **Severity:** Low
- **Confidence:** High
- **Affected components:** `SS-06`; `src/lib/sync/pullEngine.ts`
- **Evidence:** The concurrent local-delete/remote-delete convergence branch processes the event and continues before the common cursor update ([pull engine lines 166–185](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/pullEngine.ts#L166-L185)). The stale remote update guard for an already deleted local entity also continues before the common update ([pull engine lines 255–266](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/pullEngine.ts#L255-L266)); `maxAppliedSequence` is advanced later in the loop ([lines 311–321](https://github.com/Yousef-eng679/Artix/blob/0e5ab3549ef26ef34b1ffdff4b937378d2b1afdb/src/lib/sync/pullEngine.ts#L311-L321)).
- **Observed behavior:** For those events, the sequence is not included in the batch’s `maxAppliedSequence` update when the branch continues early.
- **Expected invariant:** Once a feed record has been handled as converged or intentionally ignored, cursor progress should remain explicit and consistent with that decision.
- **Execution trace:** If such an event is the highest/only currently visible row, the cursor can remain behind; a stale event may be revisited on subsequent pulls until a higher sequence advances the cursor. In the convergence case, the first pass removes the local pending delete and the same feed row may be visited a second time before the cursor advances.
- **Impact:** Repeated reads/processing, unnecessary database work and potentially misleading sync activity; no independent permanent data-loss consequence is established for this item.
- **Prerequisites:** A batch includes one of the early-continue records at or above the current cursor and no later row advances the cursor.
- **Verification:** Direct control-flow evidence; no runtime test run.
- **Recommended remediation:** Make sequence handling unconditional in a `finally`-style per-row path, or collect a safe batch cursor independent of whether the row applies, conflicts or is intentionally ignored. Be careful not to mask F-001 by treating identity sequences as commit-safe.
- **Regression protection:** Tests assert cursor progress for each branch and that an ignored stale change is not repeatedly processed when no later change exists.
- **Related findings:** F-001; fixing F-001’s committed-prefix semantics is prerequisite to a globally correct cursor.

## 12. Remediation Roadmap

### P0 — Immediate

**No P0 item is assigned in this report.** No issue meeting the prompt’s “Critical” threshold was demonstrated in this read-only pass.

### P1 — High priority

**R-001 — Correct the server change-feed cursor contract (F-001).**
- **Outcome:** Any committed remote entity mutation is eventually observed even when overlapping transactions commit out of allocation order.
- **Approach:** Adopt a commit-safe cursor protocol and migrate existing clients/cursors carefully. Evaluate a per-user locked cursor row or another durable commit-order position. Preserve backward-compatible replay or a documented full reconciliation during rollout.
- **Dependencies:** PostgreSQL migration, pull API/query semantics, local cursor compatibility, multi-client rollout plan.
- **Change risk:** High; cursor migrations and old-client compatibility affect every synced entity.
- **Regression tests:** Reversed-commit-order PostgreSQL integration test, paging/batch boundary tests, restart/replay tests.
- **Acceptance criteria:** No committed feed row can remain permanently below the client’s durable cursor without being applied or explicitly reconciled.

**R-002 — Enforce a server-owned plan/price mapping (F-002).**
- **Outcome:** Only recognized Artix Prices can grant the corresponding entitlement.
- **Approach:** Resolve a stable plan enum to price IDs inside the Edge Function; verify price/product, currency, amount, billing interval and active status in the webhook before granting Pro.
- **Dependencies:** Stripe catalog configuration, tests for webhook event shapes, handling of legacy/subscription changes.
- **Change risk:** Medium; existing subscriptions and price changes need a compatibility policy.
- **Regression tests:** Unknown/tampered price is rejected; a valid monthly/annual plan grants the expected tier; invalid product cannot grant Pro.
- **Acceptance criteria:** No browser-supplied ID can choose the entitlement independently of the server’s allowlist.

**R-003 — Make mutation idempotency atomic (F-003).**
- **Outcome:** A retry after a lost response returns the original acknowledgement and cannot overwrite later remote state.
- **Approach:** Use a server-side RPC/transaction to claim the mutation ID, apply the mutation, write the feed event/ledger, and persist an acknowledgement atomically. Return the prior result for duplicate mutation IDs.
- **Dependencies:** SQL function/RPC, adapter migration, server permission model and RLS/privilege review.
- **Change risk:** Medium-high; changes protocol behavior and retry semantics.
- **Regression tests:** Lost response, duplicate concurrent requests, ledger write failure, duplicate create after later edit.
- **Acceptance criteria:** Repeated mutation ID has exactly one business effect and returns a stable result.

**R-004 — Verify and narrow Supabase PWA caching (F-004).**
- **Outcome:** Private API data is never reused across account contexts.
- **Approach:** First reproduce with real service-worker cache behavior and inspect response `Vary` headers. Unless a deliberate cache-safe model is proven, exclude Supabase REST/Auth/Functions URLs from Workbox runtime caching and rely on Dexie for local-first workspace data.
- **Dependencies:** Cache strategy, logout/account-switch behavior and offline UX.
- **Change risk:** Low-medium; may reduce offline behavior of uncached cloud-only screens.
- **Regression tests:** Two-account online/offline switch test; inspect Cache Storage; assert no user-specific response is reused.
- **Acceptance criteria:** No cross-account data appears after logout/login, including when the network is unavailable.

### P2 — Planned

**R-005 — Serialize quota enforcement (F-005).**
- **Outcome:** Simultaneous requests cannot exceed per-user limits.
- **Approach:** Lock a stable per-user row/advisory key before checking count, or maintain atomically guarded per-user usage counters. Decide how soft-deleted entities count.
- **Dependencies:** SQL schema/trigger changes and transaction tests.
- **Change risk:** Medium; locking can lower throughput for concurrent same-user operations.
- **Regression tests:** Two or more concurrent requests at exactly one remaining slot for each quota-controlled table.
- **Acceptance criteria:** The number of successful creates never exceeds the configured limit under concurrency.

**R-006 — Restore reproducible E2E verification (F-006).**
- **Outcome:** Browser tests run from a clean checkout and are represented in CI.
- **Approach:** Add compatible Playwright dependency to package.json/lockfile and CI browser installation/job. State clearly whether E2E gates pull requests or runs on a schedule.
- **Dependencies:** Deterministic auth/test fixtures; separate safe staging backend if integration tests are needed.
- **Change risk:** Low-medium; increases CI time and may require flake control.
- **Regression tests:** `npm ci`, `npm run test:e2e -- --list`, one representative browser test.
- **Acceptance criteria:** E2E can start on a clean CI runner and results are visible alongside unit tests.

### P3 — Opportunistic

**R-007 — Make cursor advancement explicit on every pull branch (F-007).**
- **Outcome:** Handled/ignored rows do not cause repeat processing solely due to a missed cursor update.
- **Approach:** Centralize the per-row sequence/cursor accounting with commit-safe cursor semantics from R-001.
- **Dependencies:** R-001.
- **Change risk:** Low if addressed as part of cursor refactor; unsafe if patched with current identity semantics without resolving R-001.
- **Regression tests:** Repeated stale tombstone and delete-convergence event when no later sequence exists.
- **Acceptance criteria:** No event is needlessly processed repeatedly after a successful intentional disposition, without advancing past unseen committed changes.

## 15. Final Engineering Assessment

### Architectural coherence

The architecture is recognizable and largely explicit: account-scoped client databases, domain repositories, outbox-mediated local writes, pull/push engines, cross-tab coordination and a durable server change-feed all have identifiable ownership. The separation between client-held AI credentials and server-side Stripe secrets is also visible. A substantial test corpus accompanies the code.

### Correctness and data integrity

The most important guarantee—eventual delivery of every committed server-side change through the durable cursor—is not upheld by the current identity-sequence cursor contract. The retry protocol also cannot claim strict idempotency while the server mutation and ledger are separate transactions. Those issues should be addressed before relying on the sync subsystem for strong cross-device consistency.

### Security posture

This pass confirmed several useful security controls, including authenticated Edge Function requests, webhook signature verification, selected user-scoped RLS policies and a passphrase-protected AI-key vault. It also found a concrete missing price allowlist at the billing trust boundary and a service-worker caching configuration that needs validation/narrowing. The evidence does not support a blanket statement that Artix is secure or insecure; a full RLS/grants audit and live cache/billing tests are still needed.

### Test maturity and operational readiness

Unit tests are extensive and cover many modeled failure cases. However, mocks do not currently test PostgreSQL identity sequence allocation versus commit order, and the repository does not wire its listed Playwright suite into CI with the dependency in place. No test/build result was observed during this audit, so CI health remains unknown.

### Highest-value next actions

1. Fix the commit-safe feed cursor semantics and add a real PostgreSQL concurrency regression test.
2. Move idempotency enforcement into a server-side atomic mutation protocol.
3. Restrict checkout to a server-owned price map and validate webhook entitlements.
4. Prove or eliminate authenticated Supabase API caching in the service worker.
5. Serialize database quota enforcement and restore reproducible E2E execution.

**What this audit establishes:** Several critical source-level execution paths were inspected; one high-confidence sync data-integrity flaw, two additional implementation gaps and supporting verification gaps were identified with evidence and remediation guidance.

**What it does not establish:** It does not prove any issue has occurred in production, certify all security controls, measure performance, confirm the deployed database/Stripe/service-worker configuration, or establish that all 458 repository entries and all supported workflows are defect-free. Additional targeted tests and broader subsystem coverage are required for a complete audit.
